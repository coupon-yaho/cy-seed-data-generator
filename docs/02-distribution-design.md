# 분포 설계

분포가 목표에서 몇 퍼센트 흔들려도 데이터는 그럴듯해 보인다.
문제는 그 흔들림 때문에 검증 배치의 특정 분기가 영영 안 밟히거나,
반대로 정상셋에서 finding이 나온다는 점이다.
그래서 분포를 확률 문제가 아니라 제약 만족 문제로 풀었다.

## 행 합과 열 합이 동시에 성립해야 한다

요구 분포는 두 방향에서 온다. 회차 147개는 각자 발급 수가 정해져 있고(재고 × 소진율),
전역으로는 ISSUED 40%, USED 35%, EXPIRED 15%, CANCELLED 10%를 맞춰야 한다.
여기에 시간축 기울기가 겹친다. 최근 회차는 ISSUED가 우세하고 1년 전 회차는 EXPIRED가 우세해야
자연스럽다.

회차마다 독립적으로 확률 추출하면 전역 합계가 흔들린다.
전역에서 먼저 뽑아 회차에 나눠 담으면 회차별 발급 수가 안 맞는다.
시간축 가중치를 그냥 곱하면 열 합이 40/35/15/10에서 벗어난다.

IPF(Iterative Proportional Fitting)로 두 방향을 동시에 맞춘다.
행 스케일링과 열 스케일링을 번갈아 40회 돌리면 실수 해가 수렴한다.

```python
# catalog.py — ipf_integer()
x[i][j] = 시간축 버킷별 선호 가중치

for _ in range(40):
    x[i]   *= 발급수[i] / sum(x[i])        # 행 방향
    x[:,j] *= 목표[j]  / sum(x[:,j])       # 열 방향
```

결과는 300만 건에서 오차 0이다. ISSUED 1,200,000 / USED 1,050,000 /
EXPIRED 450,000 / CANCELLED 300,000.

## 정수로 내리는 데서 한 번 데었다

처음에는 소수부가 큰 칸부터 행·열 잔여가 둘 다 남은 곳에 +1 하는 그리디를 썼다.
이 방식은 잔여를 배치하지 못하고 갇힐 수 있다.
어떤 행의 잔여가 남았는데 그 행에서 쓸 수 있는 열들의 잔여가 이미 다른 행에 소진된 상태가 된다.
가능한 해가 분명히 존재하는데도 실패한다.

지금은 두 단계로 나눈다. 먼저 행 안에서만 배분해 행 합을 닫는다.
행이 닫히면 이후 어떤 조작도 행을 깨뜨리지 못한다.
그다음 열 합을 이동으로 맞춘다.

```
초과 열 jo, 부족 열 ju 에 대해
out[i][jo] > 0 이고 가중치 x[i][ju] > 0 인 행 i 를 찾아
    out[i][jo] -= 1
    out[i][ju] += 1

같은 행 안에서 열만 바꾸므로 행 합은 불변,
열 편차는 매번 2씩 줄어든다
```

이동 경로가 아예 없을 때만 실패하는데, 그때는 정말로 실행 불가능한 제약이다.

### 이 버그는 날짜가 바뀌어야 드러났다

계획은 `as_of`의 함수다. 날짜가 하루 바뀌면 만료 가능한 회차 집합이 달라지고,
그러면 가중치 0인 칸의 위치가 바뀌어 제약 구조가 통째로 달라진다.
어제 통과한 코드가 오늘 실패할 수 있다는 뜻이고, 실제로 그렇게 깨졌다.

그래서 `bin/plancheck.py`를 뒀다. DB 없이 여러 날짜와 여러 시드로 계획 단계만 돌려
불변식을 확인한다. 수 분짜리 전체 생성을 돌리기 전에 이걸 먼저 통과시킨다.

```
$ python bin/plancheck.py
검사 240건 (120일 / 3일 간격 × 시드 3개 × 2 데이터셋)
✅ 전부 통과 — 총 발급 수 · 행 합 · 열 합 · 재고 상한 · 만료 제약 · 완판 혼재
```

## 가중치 0에는 물리적 의미가 있다

`EXPIRE` 이력의 `created_at`은 `expires_at` 이후이면서 `asOf` 이전이어야 한다.
그런데 최근 회차는 `open_at + valid_days`가 아직 미래다.
여기에 EXPIRED를 배정하면 미래 시각의 이력을 써야 하고,
리플레이가 `created_at <= asOf`로 그 행을 걸러내므로 상태가 어긋나 정상셋에서 V3가 검출된다.

그래서 회차마다 `expirable`을 판정해 IPF 가중치를 0으로 만든다.
IPF가 그 15%를 만료 가능한 회차로 알아서 밀어낸다.

```python
# close_at 기준으로 보수적으로 판정한다.
# open_at 기준이면 회차 후반에 발급된 건의 expires_at 이 asOf 를 넘는다.
c.expirable = c.close_at + timedelta(days=c.valid_days) < as_of
```

생성기에 방어선을 하나 더 뒀다. 이 상황이 실제로 오면 조용히 넘어가지 않고 즉시 실패한다.
없으면 생성은 성공하는데 검증에서 정상셋 0건이 안 나온다. 디버깅 난이도가 완전히 다른 종류의 버그다.

## 발급 수도 정확히 300만

회차별 소진율을 뽑으면 합계가 목표와 안 맞는다.
`_rebalance()`가 하한과 상한을 지키며 1씩 옮겨 정확히 3,000,000을 만든다.
완판 회차는 발급이 재고와 같아 조정 대상이 아니고,
미달 회차는 재고의 50% 이상 재고−1 이하로 묶인다.

완판을 25%로 제한한 것도 의도한 값이다.
재고와 발급이 같으면 모든 회차가 완판되어 검증 배치의 "잔여재고 > 0" 분기가
한 번도 실행되지 않는다. 총재고를 393만으로 잡아 평균 소진율 79%를 만들었다.
완판 회차만 `sold_out_seconds`가 채워지고 미달 회차는 NULL이라 두 분기가 모두 데이터에 있다.

## 파레토를 대략이 아니라 정확히

상위 30% 사용자가 이력의 80%를 갖는다는 조건을 회차마다 확률로 처리하면 실제 비율이 흔들린다.
Knuth 선택 샘플링을 쓰면 정확히 `n_heavy`개가 뽑힌다.

```python
if heavy_left > 0 and rng.random() < heavy_left / (n - i):
    rank = heavy.take(); heavy_left -= 1
else:
    rank = light.take()
```

`heavy_left == n - i`가 되면 확률이 1.0이 되어 남은 자리를 전부 heavy로 채운다.
`random()`이 `[0,1)`이라 경계도 정확하다. 보정 코드가 따로 필요 없다.

heavy 풀은 각 등급 블록의 앞 30%로 정의한다.
VIP 전용처럼 등급이 제한된 회차에서 heavy 풀이 부족하면 풀 크기로 clamp하고 매니페스트에 남긴다.

## 불변식은 검증이 아니라 구성으로

위반을 만들어 놓고 걸러내는 게 아니라 애초에 생길 수 없게 만든다.

| 불변식 | 어떻게 |
|---|---|
| V6 등급 자격 | 회차 mask에 해당하는 등급 블록에서만 추출 |
| `uk_coupon_member` | 회차별 비복원 추출. 같은 회원이 두 번 나올 수 없다 |
| `uk_coupon_code` | 코드 = 발급 id의 base32 인코딩 |
| `uk_email_hash` | 이메일 로컬파트에 rank를 박아 평문이 단사. HMAC 출력도 단사가 된다 |
| `active_count = ISSUED + USED` | 생성 중 카운터로 누적. 사후 집계가 아니다 |
| 활성 usage는 USED당 1행 | 상태에 따라 usage 행을 결정론적으로 발행 |

네 번째는 ERD가 명시적으로 요구한 것이다.
`uk_email_hash`를 나중에 거는 이상 해시 충돌 0을 시드가 보장해야 하고,
충돌하면 `ADD CONSTRAINT`가 통째로 실패한다.
100만 행을 넣은 뒤 제약 생성이 한 번에 통과하는 게 이 설계의 실증이다.
난수로 이메일을 만들었다면 생일 문제로 언젠가 터진다.

## 오픈런 곡선과 요일 패턴

`issued_at` 오프셋을 `window × u³`로 앞쪽에 몰아 선착순 발급 곡선을 만든다.
완판 회차는 윈도우를 전체 시간의 2~50%로 압축해서
`sold_out_seconds`가 회차마다 다른 값이 되게 했다.

브랜드데이를 1~4주차 × 월~금 × 07~20시로 흩뿌린 것도 같은 이유다.
균등하게 깔면 요일 × 시간 히트맵이 무의미해진다.

## 일부러 이상해 보이게 만든 것

정상셋이 지나치게 깨끗하면 오히려 검증 로직의 분기를 못 밟는다.
아래는 전부 정상이고, 규칙으로 만들면 정상셋 0건이 원천 불가능해진다
([검증하지 않는 것](06-not-verified.md) 참고).

- **`issued_grade`가 현재 등급과 다른 행** — 등급 제한 회차의 3%.
  발급 후 강등된 회원이다. V6가 스냅샷만 보므로 0건이 유지되고,
  이 컬럼이 왜 있어야 하는지를 데이터로 보여준다.
- **`expires_at < asOf`인데 `status = ISSUED`** — 만료 배치가 아직 안 돈 상태.
- **재고가 남은 CLOSED 회차 75%** — "잔여재고 > 0" 분기용.
- **`phone_hash` 중복 0.5%** — 전화번호는 UNIQUE가 아니라는 설계를 드러낸다.
- **회차 재고가 템플릿 기본값과 불일치** — F6.

## 결정론

같은 `(--seed, --as-of)`면 같은 데이터가 나와야 한다.
검증 배치의 재실행 결정론을 증명하려면 데이터부터 결정론이어야 하기 때문이다.

`random` 전역 대신 `SplitMix64(seed, 스트림명)`으로 테이블과 회차별 독립 스트림을 만든다.
회원 생성 로직을 고쳐도 발급 데이터가 그대로 나온다.
`issuances.updated_at`은 `NOW()`가 아니라 마지막 이력의 `created_at`으로 확정한다.
`dataset_fingerprint`의 다섯 입력 중 하나라서 그렇다.
Faker는 `seed_instance()`로 고정하는데, 호출 순서가 곧 난수 소비 순서라 단일 루프를 유지해야 한다.

같은 시드로 두 번 생성해 TSV를 해시 비교했다.
`issuances`, `issuance_histories`, `issuance_usages`, `coupon_stocks`, `members` 전부
바이트 단위로 같았다.

```bash
for r in a b; do
  python bin/seed.py generate --dataset clean --scale 0.005 \
         --seed 777 --as-of '2026-08-01 09:00:00' --clean-out --out out/det_$r
done
for f in issuances issuance_histories coupon_stocks members; do
  diff <(cat out/det_a/$f.*.tsv) <(cat out/det_b/$f.*.tsv) >/dev/null && echo "✓ $f"
done
```

`members`만 예외적으로 같은 `AES_KEY`와 `HMAC_KEY`를 써야 바이트 단위로 같다.
IV는 결정론 RNG에서 나오지만 암호문과 해시는 키의 함수다.
`dataset_fingerprint`는 members를 입력으로 쓰지 않으니 키와 무관하게 재현된다.
